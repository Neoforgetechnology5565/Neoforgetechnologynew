# Neo Forge Technology — website + CMS

Next.js 15 (App Router, TypeScript, Tailwind) · Firebase Firestore + Auth · Cloudinary media · Vercel hosting (GitHub → `main`).

## One-time setup
1. **Firebase**: create a project → enable Firestore (production mode) and Authentication → *Email/Password*. Add your admin user under Authentication → Users. Deploy `firestore.rules` (deny-all; the server uses the Admin SDK). Create a service-account key (Project settings → Service accounts).
2. **Cloudinary**: note cloud name, API key and secret. (No upload preset needed — uploads are server-signed.)
3. **Vercel**: import the GitHub repo, set Production Branch = `main`, and add the env vars from `.env.example`. Set `ADMIN_EMAILS` to your admin email(s).
4. Visit `/admin`, sign in. On first sign-in the allow-listed, **email-verified** account receives the `admin` custom claim (the login page sends the verification email if needed). Categories and starter FAQs are seeded automatically; everything else is managed in the admin.

## Security model
- `/admin` is not linked anywhere, but protection is real: httpOnly SameSite=Strict session cookie (Firebase session cookie), verified server-side with revocation + `admin` claim in every admin page and API route; Origin check on mutations; sign-out revokes tokens.
- Firestore rules deny all client access. Inputs validated with zod and stripped of markup; media URLs must be on your Cloudinary cloud.
- Cloudinary uploads are signed per-request (folder + allowed formats fixed server-side) and go browser → Cloudinary. Public visitor uploads (contact/chat) use a separate rate-limited signer limited to JPG/PNG/WEBP/PDF. The in-memory rate limiter is best-effort on serverless; add Vercel Firewall rate limits for hard guarantees. Size limits are enforced client-side (Cloudinary plan limits apply server-side).
- PDFs are uploaded as Cloudinary image resources so page-1 thumbnails are generated by URL transformation.

## Local development
`npm i && cp .env.example .env.local && npm run dev`. For emulator testing set `FIREBASE_AUTH_EMULATOR_HOST`, `FIRESTORE_EMULATOR_HOST` and `NEXT_PUBLIC_FIREBASE_AUTH_EMULATOR_URL`.

## Notes
- Sub-categories, projects, copy, FAQs, contact links and chat settings are all data; the three divisions are structural (code).
- Migrations (`src/lib/migrations.ts`) are idempotent and run automatically on admin load; re-run from Admin → Maintenance.
- Deleting a project does not delete its Cloudinary assets.
